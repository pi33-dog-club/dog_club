# Веб-клиент клуба

React 18, TypeScript (strict), Vite и CSS Modules без CSS-фреймворков. Данные
загружаются через TanStack Query, маршруты — React Router. Типы запросов и ответов
генерируются из [OpenAPI бекенда](../backend/api/openapi.yaml), поэтому клиент
не расходится с контрактом. Экраны повторяют дизайн-макет клуба.

## Запуск для разработки

Нужны Node 20+ и npm 11.19+: npm 11.3 из Node 24.1 падает на опциональных
peer-зависимостях Vitest (`Cannot read properties of null (reading 'edgesOut')`).

```sh
cd frontend
npx -y npm@11.19.1 ci
npm run dev
```

Dev-сервер работает на `http://localhost:5173` и проксирует `/api` и `/health`
в `http://127.0.0.1:8080` (другой адрес — переменная `DOGCLUB_API_URL`). API не
включает CORS и проверяет Origin изменяющих запросов, поэтому браузер должен видеть
клиент и API на одном origin; прокси сохраняет заголовок Host.

| Команда | Что делает |
| --- | --- |
| `npm run dev` | Генерирует типы API и запускает Vite |
| `npm run typecheck` | Генерирует типы и проверяет TypeScript |
| `npm test` | Генерирует типы и запускает Vitest (jsdom) |
| `npm run build` | Типы, проверка TypeScript и сборка в `dist/` |
| `npm run api:types` | Только `src/api/schema.d.ts` из `backend/api/openapi.yaml` |
| `npm run e2e` | Браузерные тесты Playwright против запущенного стенда |

`src/api/schema.d.ts` генерируется и в Git не хранится.

Чтобы экраны были с данными, запустите стек в отдельном проекте и наполните его
`python3 scripts/club-data.py` — см. [стенд с данными](../backend/docs/operations.md#стенд-с-данными).
Логины всех ролей и общий пароль скрипт записывает в `var/club-accounts.txt`.

## Docker

Сервис `web` в корневом `compose.yaml` собирает клиент и отдаёт его через
nginx без root на `127.0.0.1:8081` (`WEB_PORT`). nginx проксирует `/api` и `/health`
в сервис `api` и добавляет CSP, `nosniff` и `Referrer-Policy`. Сборочный контекст —
корень репозитория: образу нужен `backend/api/openapi.yaml`.

```sh
docker compose up --build -d --wait web
docker compose run --build --rm web-checks
```

`web-checks` выполняет typecheck и тесты в контейнере без Node на компьютере.

Ограничение частоты входа в API считается по адресу клиента. За nginx все браузеры
приходят с адреса контейнера `web`, поэтому лимит входа (10 в минуту) становится
общим для всех пользователей этого стенда. Для локального учебного запуска этого
достаточно; заголовкам `X-Forwarded-For` бекенд намеренно не доверяет.

## Браузерные тесты

Тесты Playwright лежат в `e2e/`. Обычный запуск — из корня репозитория, на
одноразовом стенде:

```sh
python3 scripts/e2e.py                 # все тесты
python3 scripts/e2e.py -- -g expert    # аргументы после -- уходят в playwright test
python3 scripts/e2e.py --keep          # оставить стенд после прогона
```

Обход по ролям (`e2e/crawl.spec.ts`) входит под каждой из шести ролей через экран
входа и открывает разделы меню, их вкладки и по одной записи каждого вида (до трёх
переходов вглубь). Тест падает на отказах API, ошибках скрипта и консоли,
сообщениях об ошибке на экране и текстах вроде «Раздел недоступен». Ожидаемые
отказы перечислены в тесте: 401 на refresh до входа, 404 на фото собаки без фото,
404 у владельца на карточку чужой собаки-партнёра. Второй тест проверяет, что
разделы помещаются на экран шириной 375 px без горизонтальной прокрутки.

Экраны открываются через роутер, как по ссылке, без перезагрузки страницы: каждая
перезагрузка обновляет сессию, а API принимает не больше 60 refresh в минуту с
одного адреса. Тесты идут в один поток, и каждая роль входит один раз за прогон:
refresh-токены одноразовые, а вход ограничен 10 попытками в минуту (при отказе
тест ждёт минуту и повторяет вход).

Против уже запущенного стенда — контейнер `e2e` или Node на хосте:

```sh
docker compose --profile tools run --rm e2e      # логины в var/e2e/accounts.txt
cd frontend && npx playwright install chromium && npm run e2e
```

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `E2E_BASE_URL` | `http://localhost:5174` | Адрес веб-клиента |
| `E2E_ACCOUNTS` | `../var/club-accounts.txt` | Файл логинов и пароля от `club-data.py` |
| `E2E_OUT` | `../var/e2e` | Отчёт, трассы и снимки ошибок |
| `MAILPIT_URL` | `http://localhost:28025` | API Mailpit стенда |

## Структура

```text
src/
  api/          клиент openapi-fetch, ошибки RFC 9457, сессия и refresh
  auth/         AuthProvider и вызовы /auth
  app/          маршруты, меню по ролям, провайдеры
  features/     экраны по разделам: вход, аккаунт, собаки, члены клуба, ветеринария,
                племенная работа, мероприятия, дрессировка, документы, отчёты,
                администрирование, главная, экран «нет доступа»
  shared/ui/    компоненты дизайн-системы
  shared/layout/  оболочка: боковое меню, нижняя панель, переключатель профиля
  styles/       токены и глобальные стили
  test/         настройка Vitest и мок fetch
e2e/            браузерные тесты Playwright и их помощники
```

## Сессия и права

- Access-токен (10 минут) хранится только в памяти вкладки, refresh — в HttpOnly
  cookie `dogclub_refresh`. После перезагрузки страница восстанавливает сессию
  запросом `POST /auth/refresh`.
- Refresh ротируется, а повтор старого значения бекенд считает атакой и отзывает
  сессию. Поэтому обновления сериализованы: один общий запрос внутри вкладки и
  Web Locks между вкладками.
- На 401 клиент один раз обновляет токен и повторяет запрос. Эндпоинты входа,
  активации и восстановления пароля не повторяются и не получают Bearer.
- В сессии активен один профиль, права не складываются. Меню строится по роли
  активного профиля; раздел чужой роли показывает «Нет доступа» с подсказкой
  переключить профиль. При смене профиля или аккаунта кеш запросов очищается.
- После смены пароля бекенд завершает все сессии; клиент возвращает на вход
  с сообщением.

## Компоненты

`shared/ui` повторяет дизайн-систему: кнопки (primary — малина, одна на экран;
save — ink; secondary — контур; danger — текстовая, только через диалог причины),
поля с подписью, подсказкой и ошибкой, выбор файла с русской кнопкой, счётчик
пароля от 15 символов, чипы статусов, карточки, сегментные вкладки с клавиатурой,
сообщения ошибок API (текст сервера и список ошибок по полям; на конфликт версии —
кнопка «Обновить») и диалог обязательной причины для исправлений и отмены записей.

Ошибка заполнения всегда видна под полем: и от проверки браузера, и из ответа
сервера (`errors[].field` совпадает с именем поля формы). Формы работают с
`noValidate`: при сохранении `reportInvalid` проверяет все поля разом, вместе со
своими правилами формы, и ставит фокус на первое ошибочное. Всплывающие подсказки
браузера не показываются, текст не зависит от языка браузера; поле из одних
пробелов считается пустым. Кнопка сохранения не блокируется молча: нажатие
объясняет, что исправить (`FormDialog` — свойства `check` и `notReady`).
Простые правила сервера — длина, диапазон, формат телефона, email и логина,
порядок дат — форма проверяет до отправки (`shared/rules.ts`, `localProblem`).
Общий блок над кнопкой повторяет только ошибки, которых нет под полями.
Технические значения — коды ошибок, номера запросов, версии записей — на экран
не выводятся.

Шрифты Fira Sans Extra Condensed 800 и Onest подключены локально через
Fontsource: внешних запросов нет. Иконки — Lucide со штрихом 2.

## Собаки и члены клуба

- Списки с поиском, фильтрами в адресной строке и подгрузкой «Следующие 50»
  по курсору `after`. Владелец видит только своих собак и свою карточку («Моя
  карточка», `/me`); при неактивном членстве — экран «Членство неактивно».
- Карточка собаки: шапка со статусом, плитки владельцев, даты регистрации,
  титулов, вкладки «Родословная», «Титулы», «Владельцы», «История».
  Неактивный статус (лаб. 3) показывает предупреждение, что новые записи закрыты.
- Родословная: документ (номер и организация) делает её известной на три
  поколения. Мать и отец — собака клуба, внешние сведения или «неизвестен».
  Поиск родителя идёт по `GET /dogs?sex_id=`, поэтому в подсказке только суки
  или только кобели. Дерево показывает родителей, а сотруднику и руководителю —
  ещё и дедов из карточек родителей.
- Исправления титула и даты регистрации требуют причину; она попадает в историю.
- Фото собаки: портрет в шапке карточки, плитки собак на «Главной» владельца,
  «сторис» подбора пары и карточка пациента у ветеринара. Без фото — значок.
  Изображение требует токена, поэтому его байты загружаются запросом
  (`fetchBlob`) и показываются через object URL. Загружает, заменяет и убирает
  фото только сотрудник (JPEG или PNG до 5 МиБ, проверяется и до отправки);
  у фото своя версия, карточка собаки от него не меняется.
- Карточка члена клуба: контакты и адреса (добавить, заменить, удалить), собаки
  человека и история.
- Регистрация и правки доступны только профилю «Сотрудник клуба». Руководитель
  видит те же экраны без кнопок изменения.
- Каждое изменение отправляет `version`. На конфликт (409) форма и диалог
  предлагают «Обновить», ошибки полей (422) подсвечиваются у своих полей.

## Ветеринария

- Ветеринар работает в разделах «Пациенты» и «Препараты». Поиск пациентов
  (`GET /veterinary/dogs`) не раскрывает владельцев. Отдельного чтения собаки
  по ID у ветеринара нет, поэтому карточка пациента берёт его тем же поиском
  с `after=ID-1&limit=1`.
- Вкладка «Здоровье» (у ветеринара — в карточке пациента, у сотрудника,
  руководителя и владельца — первая вкладка карточки собаки) показывает допуск
  к мероприятиям и вязке с причинами, прививки, осмотры с диагнозами
  и заключения. Остальные профили видят её только для чтения.
- Ветеринар вносит прививки, осмотры и заключения. Исправить или отметить
  ошибочной можно только свою запись, всегда с причиной; ошибочные записи
  остаются зачёркнутыми.
- Лаб. 3: для собаки не на учёте кнопки новых осмотров и прививок скрыты.
  Справочники собак ветеринару недоступны, поэтому активность он определяет
  по статусу «На учёте»; сервер всё равно отклонит запись. В форме прививки
  подсказка называет дату, раньше которой новая доза того же препарата
  не пройдёт, а отказ сервера (422) показывается у поля даты.
- Заключение строится на собственном осмотре ветеринара, поэтому кнопка «Новое
  заключение» видна только при своём действующем осмотре; иначе — пояснение.
  Для собаки не на учёте заключение можно выдать по уже внесённому осмотру.
  «Допущена» требует срока и прививок-оснований. Своё заключение автор
  исправляет с причиной (все поля, включая решение и основания) или отмечает
  ошибочным и выдаёт новое.
- «Препараты»: название, производитель, срок действия и интервал
  ревакцинации; исправление с причиной и история.

## Племенная работа

- Раздел `/breeding`: вкладки «Заявки», «Вязки», «Помёты». Сотрудник ведёт
  процесс, эксперт решает по заявкам (ожидающие наверху), руководитель читает.
  Владелец видит заявки, вязки и помёты своей собаки на вкладке «Вязки» её
  карточки, без проверки пары: сервер её владельцу не отдаёт.
- Записи хранят только ID собак. Клички сотрудник, руководитель и эксперт
  получают из `GET /breeding/dogs?after=ID-1&limit=1`; эксперт карточек собак
  не открывает. Владелец видит кличку только своей собаки, партнёр остаётся
  «собака №ID».
- Карточка заявки: проверка пары на текущий момент — блокирующие причины
  малиновыми чипами (в том числе правила лаб. 3: «Сука/Кобель не на учёте»,
  «Родитель и потомок», «Общий родитель», «Общий предок в 3 поколениях»),
  предупреждения жёлтыми, общие предки, допуск к вязке и родословная каждой
  собаки. «Одобрить» недоступна, пока есть блокирующие причины. Ниже решения
  эксперта и история.
- Сотрудник исправляет заявку с причиной (она вернётся к эксперту), отменяет
  её и проводит вязку в одобренную дату. В карточке вязки уточняет исход
  и регистрирует помёт; в карточке помёта регистрирует щенков (порода,
  дата рождения и родители берутся из помёта), связывает существующие
  карточки и снимает ошибочные связи. Интервал меньше 365 дней показывается
  предупреждением.
- Подбор пары (лаб. 3): кнопка «Подобрать пару» на вкладке «Вязки» у
  сотрудника и руководителя для собаки на учёте. У эксперта карточек собак нет,
  поэтому подбор для суки и кобеля открывается ссылками со страницы заявки.
  Кандидаты — карточки «сторис»; у сотрудника «Создать заявку» подставляет пару
  в форму.

## Мероприятия

- Раздел `/events`: календарь с поиском, фильтрами по типу, состоянию и
  периоду. Сотрудник и руководитель видят все мероприятия и вкладку
  «Площадки», эксперт — только назначенные, владелец — все, кроме черновиков.
- Время вводится и показывается по часам места проведения: в форме выбирается
  часовой пояс IANA, а значение уходит на сервер в RFC 3339 со смещением этого
  пояса. Смещение считает `Intl`, без библиотек, включая переход на летнее
  время. Под временем подписаны пояс и смещение.
- Карточка мероприятия: «Обзор» (описание, смена состояния с причиной,
  назначение экспертов), «Программа» (классы с возрастом в месяцах и
  выступления), «Участники», «Результаты», «История». Начать мероприятие
  до его начала нельзя: кнопка неактивна с пояснением.
- Сотрудник записывает собаку с представителем из её текущих владельцев или
  человека без собаки, пока запись открыта. В карточке записи — текущая
  проверка допуска с причинами по-русски, включая правила лаб. 3: «Собака не
  на учёте» и «Родословная не известна на три поколения». Медицинский допуск
  показан только решением и основаниями, без текста осмотра.
- При причине «Родословная не известна на три поколения» сотрудник видит
  в текущей проверке ссылку «Заполнить родословную» на вкладку родословной
  собаки; в снимке явки ссылки нет.
- После явки карточка показывает сохранённый снимок проверки, а не текущую:
  правка карточки собаки после выставки не делает участие «недопущенным».
- Назначенный эксперт подтверждает квалификацию, вносит, исправляет и
  отмечает ошибочными результаты. Владелец видит только свои записи и
  результаты своих собак, без истории всего мероприятия.

## Дрессировка

- Раздел `/training`: журнал проведённых занятий с фильтрами по собаке,
  виду, инструктору и периоду. Сотрудник и руководитель видят все занятия,
  владелец — занятия своих текущих собак. В карточке собаки та же таблица
  на вкладке «Дрессировка».
- Вносит занятие только сотрудник с допуском инструктора и только по
  разрешённым видам. Без допуска вместо кнопки — пояснение: допуск выдаёт
  администратор. Исправляет и отменяет занятие его автор.
- Время вводится по часам места занятия, как в мероприятиях; занятие
  в будущем не принимается. Для собаки не на учёте новое занятие закрыто
  (лаб. 3). Занятие можно связать с записью собаки на мероприятие «Занятие».
- Медицинский допуск показан дважды: при внесении и сейчас на те же даты,
  только решением и основаниями. Старые записи без часового пояса только
  читаются.

## Документы

- Раздел `/documents`: реестр с поиском по номеру, типу и дате выдачи.
  Набор записей определяет сервер: сотрудник видит всё, ветеринар —
  медицинские документы, эксперт — племенные и своих мероприятий, владелец —
  выданные ему. Карточки собаки, члена клуба и мероприятие открывают реестр
  с готовым фильтром.
- Сотрудник оформляет общие и племенные документы, ветеринар — медицинские:
  запись реестра, исправление и отмена с причиной, загрузка копии
  (PDF, JPEG, PNG до 10 МиБ, проверяется и до отправки) и выпуск PDF-формы
  по типу документа. Ветеринарную справку выпускают только по своему
  действующему осмотру.
- Файлы скачиваются через API с токеном сессии и сохраняются как вложение.
  Если после выпуска формы сведения изменились, у файла отметка «Сведения
  изменились»; прежний PDF не меняется. Загрузка и скачивание идут через
  `src/api/files.ts` с тем же однократным обновлением сессии, что и JSON-запросы.

## Отчёты

- Раздел `/reports` для сотрудника и руководителя: период задаётся явно,
  отчёт строится по кнопке. Показатели за период, текущие итоги на момент
  формирования и полнота дат; нули не скрываются. Выгрузка в PDF и CSV
  скачивается файлом.

## Администрирование

- «Пользователи» (`/admin/users`): список учётных записей, приглашение
  с первым профилем и необязательной карточкой члена клуба, блокировка,
  привязка к карточке. В карточке пользователя — все его профили с
  включением и отключением и действующее приглашение с повтором кода или
  отменой; их отдают `GET /users/{userID}/profiles` и
  `GET /users/{userID}/invitation`, так что всё доступно и после перезагрузки.
- «Допуски инструкторов» (`/admin/instructors`): допуск выдаётся профилю
  сотрудника, с видами дрессировки и основанием, которое видит только
  администратор; у каждого допуска своя история.
- «Состояние системы» (`/admin/system`): время работы, пул PostgreSQL,
  очередь писем и запросы по маршрутам; обновляется раз в 30 секунд.
- Ответы 409 о состоянии аккаунта (последний администратор, занятый логин)
  показывают текст сервера, а не сообщение о конфликте версий.

## Главная

- Владелец: карточки своих собак с допуском к мероприятиям, ближайшие
  мероприятия, последние документы. Неактивное членство показывает пояснение
  вместо разделов.
- Сотрудник и руководитель («Обзор»): текущие итоги клуба, заявки на вязку,
  ждущие эксперта, ближайшие мероприятия и пропуски дат со ссылкой на отчёт.

## Состав

Вход, приглашение и восстановление пароля, оболочка с меню по ролям,
переключатель профиля, аккаунт и смена пароля, сервис `web`, скрипт
тестовых данных, экраны собак и членов клуба, ветеринария, племенная работа,
мероприятия, дрессировка, документы, отчёты, администрирование и главные
страницы. У каждого раздела меню есть экран.
