# Ветеринарный учёт

Реализованы осмотры, диагнозы, вакцинации, расчёт двух сроков, медицинские
заключения для мероприятий и племенной работы, проверка оснований и история.
Основания: ТЗ §4.4, PDF 14–15, M5 на PDF 26–27; актуальное описание предметной
области, PDF 3–4; логическая и физическая схемы второго PDF (2–3) и схема
третьего PDF (5). История изменений — в [аудите](database-audit.md).

## Доступ

| Активный профиль | Чтение | Запись |
| --- | --- | --- |
| veterinarian | Медицинские сведения всех собак, поиск пациентов, справочники | Собственные осмотры, вакцинации и заключения; препараты |
| staff, leader | Медицинские сведения всех собак, история, справочники | Недоступна |
| owner | Только текущие собственные собаки при активном членстве; справочники | Недоступна |
| admin, expert | Ветеринарный раздел недоступен | Управление аккаунтами остаётся в auth |

Права профилей не объединяются. Для внесения данных ветеринару необходима
первоначальная связь аккаунта с карточкой человека через admin API; её ID
сохраняется как исполнитель осмотра/вакцинации. Статус членства ограничивает
owner, а профессиональные действия ветеринара сохраняются при неактивном
членстве. Ветеринар без связи может читать, но получает 403 при записи.

Изменять или отмечать ошибочной можно собственную клиническую запись.
Другой ветеринар читает историю и создаёт свой осмотр/заключение. Препараты —
общий справочник: любой ветеринар с карточкой может исправить их с причиной.
Автор медицинской записи определяется сервером; передать другого исполнителя
в JSON нельзя. Старые записи с неизвестным автором остаются доступными для
чтения, присвоение их авторства текущему пользователю не выполняется.

Неактивное членство закрывает весь owner-раздел: пациентов, медицинские записи,
статус, историю и справочники. Управление сессией и переключение другого
включённого профиля сохраняются. После передачи собаки старый владелец
немедленно теряет чтение записей и истории. Чужая собака для owner — 404,
неактивное членство/неподходящий профиль — 403. Проверка производится в БД
на каждом запросе, без ожидания истечения JWT.

Для работы ветеринара есть отдельный поиск пациентов. Он возвращает Summary
животного, без ID владельцев, ФИО, контактов и адресов. Общий CRUD dogs по-прежнему
доступен по правилам [модуля собак](dogs.md).

## Осмотры и диагнозы

Осмотр содержит дату, описание состояния, результат, рекомендации, диагнозы,
исполнителя, version и is_void. Поля description/result/recommendations — до
4000 Unicode-символов каждое после удаления краевых пробелов, без управляющих
знаков. В осмотре до 100 разных заболеваний из существующего справочника.

Наследственность задаётся у каждого диагноза через is_hereditary:
true — да, false — нет, null или отсутствие — не установлено. Она не выводится
автоматически из названия заболевания и не создаёт автоматического запрета
на вязку. Первоначальные семь заболеваний сохранены; API справочника заболеваний
доступен только для чтения. Дополнительные клинические сведения
можно сохранить в тексте результата; расширение справочника требует отдельного
согласования данных.

Даты медицинских процедур принимаются как YYYY-MM-DD: не раньше рождения
собаки и не позже текущей даты UTC. Исходные timestamp без часового пояса не
меняются: новые даты имеют время 00:00:00, PUT той же даты сохраняет прежнее
время старой записи. В ответах используется календарная дата, время аудита —
timestamptz. Изменение даты рождения в dogs проверяется по действующим
медицинским записям; рождение после осмотра/вакцинации отклоняется.

## Препараты и автоматический расчёт

Для препарата ветеринар задаёт name, необязательный maker и два независимых
периода: validity и revaccination. Каждый имеет value от 1 (не больше 100 лет: 36500 дней или 1200 месяцев) и unit
days или months. Название/производитель — до 100 символов. Сроки задаются по
подтверждённым сведениям о конкретном препарате. Начальных препаратов и
универсальных медицинских интервалов нет.

Вакцинация принимает только date и vaccine_type_id. Сервер вычисляет:

- valid_until = дата проведения + validity;
- next_date = дата проведения + revaccination.

days прибавляет календарные дни. months прибавляет календарные месяцы с
ограничением дня концом целевого месяца: 31 января 2024 + 1 месяц = 29 февраля,
29 февраля 2024 + 12 месяцев = 28 февраля 2025. Переполнение диапазона 0001–9999
отклоняется; неизвестные единицы не угадываются. Дата valid_until включительна.
Наступление next_date само по себе не означает окончания действия вакцинации.

Пример структуры запроса POST /vaccine-types (это тестовые данные для проверки
расчёта, не медицинские настройки для рабочей базы):

```json
{
  "name": "Тестовый препарат",
  "maker": "Тестовый производитель",
  "validity": {"value": 1, "unit": "months"},
  "revaccination": {"value": 20, "unit": "days"}
}
```

POST /dogs/{dogID}/vaccinations с date=2024-01-31 и ID этого тестового препарата
вернёт valid_until=2024-02-29 и next_date=2024-02-20.

В записи сохраняется снимок препарата с обоими периодами и версией справочника.
Исправление справочника не меняет старые вакцинации. Явная коррекция даты или
препарата пересчитывает сроки по текущим настройкам и сохраняет прежние значения
в истории. PUT с неизменными датой и препаратом сохраняет прежний снимок и сроки.
При неизвестных периодах/единицах новая вакцинация отклоняется с 422.

Окна ревакцинации одного препарата у собаки не пересекаются (лаб. 3,
fn_prevent_active_vaccination). Интервал дозы — [date, next_date): новая или
исправленная доза отклоняется с 422 по полю date, если её интервал пересекается
с другой неаннулированной дозой того же vaccine_type_id. Доза в сам день
next_date прежней допустима; доза задним числом внутрь чужого окна — нет. Старые
записи без next_date не учитываются. Чтобы внести дозу раньше срока, ошибочную
запись сначала аннулируют. Разные препараты проверяются независимо.

## Неактивные собаки

Статусы «Снята с учёта», «Умерла», «Потеряна», «Исключена» имеют is_active=false
в GET /dog-dictionaries (лаб. 3, fn_dog_active_check). Для такой собаки создание
и исправление осмотров и вакцинаций отклоняется с 422 по полю dog_id; аннулирование
ошибочных записей и чтение остаются доступны. Медицинские заключения этим правилом
не ограничиваются. После возврата статуса «На учёте» запись снова разрешена.

## Медицинская часть допуска

Заключение связано с собственным осмотром ветеринара. purpose — events или
breeding, decision — allowed, denied или not_assessed. Назначения независимы.
Для allowed обязательны valid_until не раньше даты осмотра и от одной до 100
разных вакцинаций этой же собаки. Они должны быть действительны на дату осмотра,
иметь известный срок, быть проведены не позднее осмотра и не быть отменены.
Для denied/not_assessed сроки и основания вакцинации не передаются.
Комментарий — до 4000 символов.

Пример POST /dogs/{dogID}/clearances:

```json
{
  "examination_id": 12,
  "purpose": "events",
  "decision": "allowed",
  "valid_until": "2027-06-30",
  "comment": "Заключение по результатам осмотра",
  "vaccination_ids": [34]
}
```

ID и даты в примере необходимо заменить существующими медицинскими данными.
Система не подбирает необходимые прививки по названию препарата: основания
явно выбирает ветеринар. Общих требований для всех мероприятий или пород нет.

GET /dogs/{dogID}/medical-status показывает состояние на текущую дату UTC
отдельно для events и breeding. Для каждого назначения выбирается последнее
заключение по дате/времени осмотра, затем по ID заключения. Позднее внесённая
запись старого осмотра не перекрывает более новое обследование. Новый осмотр
без заключения не заменяет предыдущее заключение.

Результаты: allowed, denied, not_assessed, review_required. Последний означает,
что нужно обновить оценку или основания, а не автоматически установленную
болезнь. API возвращает причины и ID проблемных вакцинаций. Эффективный
valid_until разрешения — самая ранняя дата среди заключения и выбранных оснований.

Истечение, отмена последнего заключения или его осмотра не возвращает старое
разрешение. Отмена или истечение выбранной вакцинации закрывает подтверждённый
допуск; неизвестный срок также требует проверки. Новая прививка автоматически
не подменяет старое основание: ветеринар явно обновляет заключение. Неуказанные
старые или дополнительные вакцинации на это разрешение не влияют.

При исправлении даты осмотра/вакцинации проверка статуса снова учитывает
хронологию оснований. Если исправленная вакцинация оказалась позже осмотра,
понадобится новое решение. Назначение и осмотр уже созданного заключения не
переносятся при PUT: иначе могло бы восстановиться более старое разрешение.
Для исправления такой ошибки отметьте запись недействительной и создайте новую.

Это медицинская часть межмодульных проверок. Порода, родословная, членство,
возрастные классы и условия конкретного мероприятия проверяются своими модулями.

## Маршруты

Префикс `/api/v1`, Bearer access JWT. Все новые POST возвращают 201 и Location,
исправления и /void — 200 с полной записью. DELETE медицинских записей нет.
JSON до 16 КиБ, неизвестные поля, включая вложенные, отклоняются; ошибки RFC 9457.
Точные DTO и ответы — в [OpenAPI](../api/openapi.yaml).

| Маршрут | Назначение |
| --- | --- |
| GET /veterinary/dogs | Поиск пациентов; фильтры q, breed_id, status_id, owner_id, after, limit |
| GET /veterinary-dictionaries | Заболевания и препараты |
| POST /vaccine-types | Добавление препарата ветеринаром |
| GET, PUT /vaccine-types/{typeID} | Чтение/исправление препарата |
| GET /vaccine-types/{typeID}/history | История препарата: veterinarian, staff, leader |
| GET, POST /dogs/{dogID}/examinations | Список/создание осмотров |
| GET, PUT /dogs/{dogID}/examinations/{examinationID} | Чтение/исправление осмотра |
| POST /dogs/{dogID}/examinations/{examinationID}/void | Отметка ошибочного осмотра |
| GET, POST /dogs/{dogID}/vaccinations | Список/создание вакцинаций |
| GET, PUT /dogs/{dogID}/vaccinations/{vaccinationID} | Чтение/исправление вакцинации |
| POST /dogs/{dogID}/vaccinations/{vaccinationID}/void | Отметка ошибочной вакцинации |
| GET, POST /dogs/{dogID}/clearances | Список/создание заключений |
| GET, PUT /dogs/{dogID}/clearances/{clearanceID} | Чтение/исправление заключения |
| POST /dogs/{dogID}/clearances/{clearanceID}/void | Отметка ошибочного заключения |
| GET /dogs/{dogID}/medical-status | Текущий медицинский допуск и причины |
| GET /dogs/{dogID}/veterinary-history | История клинических изменений |

Клинические списки и история используют after/limit, ответ records и next_after.
Порядок возрастающий по ID записи, limit 1–100, по умолчанию 50; null в next_after
означает конец. after истории — ID изменения. Повтор параметров отклоняется.
Поиск пациентов возвращает dogs/next_after по контракту dogs; персональных
данных владельца в ответе нет.

## Версии, история и границы модулей

Каждая медицинская запись и препарат имеют собственную version. PUT и /void
требуют её и reason длиной 1–500 символов. PUT заменяет редактируемые поля
целиком; пропущенные необязательные поля очищаются. Старая версия или повторная
отмена дают 409 veterinary_conflict. Отменённые записи сохраняются, не изменяются
и не восстанавливаются; для новых сведений создайте новую запись.

Вакцинации и осмотры разных собак не взаимозаменяемы. Составные FK заключений
и оснований дополнительно защищают это в PostgreSQL. При изменении собаки
проверяется доступ по текущему владению, не по бывшему владельцу из истории.

veterinary_changes атомарно хранит снимки до/после, тип и ID объекта, исполнителя,
причину, request_id и время. У истории препарата dog_id=null, у клинической
истории есть dog_id. Ошибка записи истории откатывает все поля, связи и версию.
История недоступна для редактирования. Срок её хранения требует отдельного
решения перед эксплуатацией.

Все операции выполняются через auth.Service.WithAccess в общей транзакции
и под общей с auth/members/dogs advisory lock. Публичные методы dogs проверяют
пациента и текущего владельца, members — активное членство и ссылки на людей.
Чужие приватные репозитории не используются. Публичная DogDatesPolicy передаёт
dogs проверку даты рождения через небольшой интерфейс без циклического импорта.
Чтения также сериализуются; внешнее I/O под блокировкой не выполняется.

503 veterinary_unavailable скрывает SQL и параметры соединения. Медицинские
тексты, персональные данные, тела, query и токены в технические логи не попадают.

## Миграция и старые данные

00006 сохраняет составные PK осмотров/вакцинаций, добавляет nullable-наследственность,
два периода препарата с единицами, снимки/авторов/версии/признаки отмены,
veterinary_clearance, clearance_vaccination и veterinary_changes. После миграции
45 прикладных таблиц, история Goose и 69 FK. Начальные 68 справочных значений
не меняются, препараты и рабочие пациенты не создаются.

Старое validity_period без единицы не трактуется как дни или месяцы. У старых
вакцинаций не вычисляются неизвестные сроки, не назначается фиктивный автор;
сохраняются исходные next_date и время процедуры. Неизвестная наследственность
остаётся null. Down требует пустых клинических записей, истории и отсутствия
настроенных препаратов: новые сведения нельзя безопасно вернуть в старую модель.

## Проверка

Запуск, миграции и аккаунты — в [README](../../README.md) и [auth.md](auth.md).
Под staff создайте карточку ветеринара, под admin привяжите её к аккаунту через
PUT /users/{userID}/member, назначьте профиль veterinarian и переключитесь на него.
Подготовьте собаку и владельца по [dogs.md](dogs.md). Добавьте препарат с
подтверждёнными параметрами, вакцинацию, осмотр и заключение с её ID.

Проверьте GET medical-status, затем /void выбранной вакцинации с version/reason:
статус должен стать review_required. Добавление новой вакцинации его не изменяет;
после явного обновления оснований заключения он снова может стать allowed.
История покажет все исправления. Проверьте owner только на своей собаке и
немедленное закрытие раздела после смены владельца/статуса членства.

```bash
gofmt -l cmd internal migrations api
go test -race -count=1 ./...
export DOGCLUB_TEST_DATABASE_URL="$DATABASE_URL"
go test -race -count=1 -tags=integration ./...
go vet -tags=integration ./...
go build -o bin/ ./cmd/...
go mod verify
git diff --check
```

Все тесты прошли, включая PostgreSQL 18.6, реальные ответы OpenAPI, месяцы/дни,
високосные даты, неизвестную наследственность, снимки препаратов, независимые
назначения, сроки оснований, отсутствие возврата старого разрешения, авторство,
владельцев/членство/профили, конкурентные версии и полный откат при отказе истории.
Миграционные тесты проверили все шесть Up/Down и сохранность старых значений.

Настоящие migrate/admin/API проверены с Mailpit на отдельной БД: все основные
ветеринарные сценарии, CSRF, безопасные логи, readiness и SIGTERM=0. Одноразовая
БД удалена. Клинические процедуры, люди и препараты в рабочую БД тестами
не добавлялись.

Шестая миграция применена к рабочей локальной БД: шесть версий applied,
46 таблиц с Goose, 69 FK. Людей, аккаунтов, собак, осмотров, вакцинаций и
препаратов нет. Проверены readiness 200, безопасные ответы/логи и SIGTERM=0.

Смежные процессы описаны в разделах [уведомлений](notifications.md),
[документов](documents.md), [племенного учёта](breeding.md) и [мероприятий](events.md).
Автоматического назначения медицинских нормативов и объединения прав профилей нет.

## Автоматические напоминания

Необязательные `replaces_vaccination_ids` доступны в DTO создания,
исправления и чтения вакцинации. Они заменяют только будущие напоминания
по прежним процедурам и не меняют медицинские основания допуска.
Правила, пример JSON и отправка через Mailpit: [notifications.md](notifications.md).
