# Члены клуба

Реализованы карточки людей, контакты и адреса, статусы членства, поиск,
история изменений и первоначальная привязка аккаунта. Основание: ТЗ §4.2,
страницы PDF 13–14 и исходная физическая схема. Ограничения переноса описаны
в [аудите схемы](database-audit.md).

## Доступ

| Активный профиль | Чтение карточек и истории | Изменения |
| --- | --- | --- |
| staff | Все | Создание и редактирование всех карточек, контактов и адресов |
| leader | Все | Недоступны |
| owner | Только своя при активном членстве | Недоступны |
| admin | Общий каталог недоступен | Первоначальная привязка аккаунта через auth API |
| veterinarian, expert | Общий каталог недоступен | Медицинские и экспертные действия — в соответствующих модулях |

При неактивном членстве весь раздел владельца закрыт: карточка, история,
справочники. Статус проверяется при каждом обращении; ждать истечения JWT
не нужно. Аккаунт и другие включённые профили сохраняются; доступны account
controls, включая выход и переключение профиля. Восстановление активного членства
возвращает owner-доступ, если профиль включён, аккаунт и сессия действуют.
Полная блокировка аккаунта продолжает отзывать все сессии.

Текущие справочники доступны только для чтения. Активность определяется значением
«Активный», а не числовым ID. Другие статусы не разрешают доступ владельцу.
Переименование/расширение справочника потребует согласования его семантики.

Карточка может существовать без аккаунта. Владелец без привязанной карточки
не получает доступа к разделу. Один аккаунт связан максимум с одной карточкой,
одна карточка — максимум с одним аккаунтом. Приглашение может сразу указывать
существующий club_member_id. Для аккаунта без связи admin выполняет
`PUT /api/v1/users/{userID}/member` с `{"member_id":123}`. Повтор той же связи
идемпотентен; перепривязка/отвязка не поддерживаются. Связь фиксируется в auth_events.
Карточка и роли доступа автоматически друг друга не создают.

Старая колонка club_member.role_id удалена по выбору пользователя. Единственный
источник ролей доступа — профили аккаунта. Справочник role сохранён; старые
значения не превращаются в полномочия. Первому администратору для ведения карточек
нужно назначить отдельный профиль staff через admin API и переключиться на него.

## Маршруты

Все пути имеют префикс `/api/v1`, нужен Bearer access JWT. DTO и ошибки описаны
в [OpenAPI](../api/openapi.yaml). JSON ограничен 16 КиБ, неизвестные поля отклоняются.

| Метод и путь | Результат |
| --- | --- |
| GET /members | Список без вложенных контактов/адресов, 200 |
| POST /members | Созданная полная карточка, 201 и Location |
| GET /members/me | Своя связанная карточка, 200 |
| GET /members/{memberID} | Полная карточка с контактами и адресами, 200 |
| PATCH /members/{memberID} | Обновлённая полная карточка, 200 |
| GET /members/{memberID}/history | Страница истории, 200 |
| POST /members/{memberID}/contacts | Добавление контакта; обновлённая карточка, 200 |
| PUT /members/{memberID}/contacts/{contactID} | Полная замена контакта этой карточки; карточка, 200 |
| DELETE /members/{memberID}/contacts/{contactID}?version=N | Удаление контакта; карточка, 200 |
| POST /members/{memberID}/addresses | Добавление адреса; карточка, 200 |
| PUT /members/{memberID}/addresses/{addressID} | Полная замена адреса этой карточки; карточка, 200 |
| DELETE /members/{memberID}/addresses/{addressID}?version=N | Удаление адреса; карточка, 200 |
| GET /member-dictionaries | Статусы членства, типы контактов и адресов, 200 |
| PUT /users/{userID}/member | Первоначальная привязка аккаунта администратором, 204 |

Чужая карточка/история для owner возвращает 404; отсутствие своей связи или
неактивное членство — 403. Неподходящий активный профиль также даёт 403.

## Поля и валидация

Карточка: id, full_name, date_of_birth, membership_date, membership_status
`{id,name}`, version, массивы contacts и addresses. При создании обязательны
full_name и membership_status_id. ФИО: 1–150 Unicode-символов после удаления
краевых пробелов, без управляющих символов. Обязательное отчество не навязывается.

Даты передаются как YYYY-MM-DD или null. Дата рождения — не ранее 1900-01-01. Будущие даты относительно UTC и
вступление до рождения отклоняются. Исходные типы date и timestamp без часового
пояса сохранены. Новая дата вступления имеет время 00:00:00; PATCH без этого
поля сохраняет прежнее время. Представление и снимки истории используют дату.

PATCH требует version и хотя бы одно изменяемое поле. Пропущенные поля
сохраняются; null очищает только дату рождения/вступления. role_id не принимается.

Контакт: version, type_id, value. Email приводится к нижнему регистру, до 254 байт,
без имени получателя. Телефон сохраняет форматирование: 7–15 цифр, до 50 байт,
допустимы пробелы, +, скобки, точка и дефис. Код страны не подставляется;
8 и +7 автоматически не приравниваются. Несколько контактов одного типа допустимы;
глобальной уникальности нет. Email карточки не меняет email входа/восстановления.

Адрес: version, type_id, locality, street, building_number, apartment_number.
Населённый пункт обязателен. Пределы: населённый пункт/улица — 100 символов,
дом/квартира — 20. В PUT пропущенные необязательные части очищаются.
Адрес, используемый мероприятием, нельзя изменить или удалить: ответ 409.
Физического удаления карточки нет; прекращение членства отражается статусом.

## Поиск, версии и история

GET /members принимает q (до 254 символов), membership_status_id, after, limit.
Поиск по подстроке ФИО/email не учитывает регистр. Телефон дополнительно ищется
по цифрам без форматирования. %, _ и обратная косая черта — обычные символы.
SQL-параметры используются для всех значений клиента.

Порядок — по возрастающему ID. after — последний ID предыдущей страницы,
limit — 1–100 (50 по умолчанию). Ответ: members и next_after; null означает конец.
История использует after как ID записи истории и такой же limit. Повтор одного
параметра страницы отклоняется. У истории хронологический порядок по ID.

Каждое изменение карточки/контакта/адреса увеличивает общую version. Передавайте
последнюю версию в JSON либо в query для DELETE. Устаревшая версия даёт
409 member_conflict; перечитайте карточку. Ошибка дочерней записи не меняет
данные, версию и историю, даже если её ID существует у другого человека.

member_changes хранит снимки до/после (при создании before=null), тип действия,
ID аккаунта и активного профиля исполнителя, роль, request_id и changed_at.
Снимки содержат персональные данные и подчиняются той же матрице доступа;
в технические логи не выводятся. API изменения истории нет. Политика хранения
истории требует отдельного решения перед эксплуатацией.

members использует публичный auth.Service.WithAccess: транзакцию, общую с auth
advisory lock и повторную проверку аккаунта/сессии/профиля. Карточка, версия и
история сохраняются атомарно. Приватные репозитории других модулей не используются.
Чтения members сейчас также сериализуются этой блокировкой; при росте нагрузки
стратегию чтения следует пересмотреть. Внешнее I/O в транзакции не выполняется.

## Ручная проверка

Запуск, экспорт .env и приглашение первого администратора — в [README](../../README.md)
и [auth.md](auth.md). В API-клиенте войдите как admin, возьмите свой user.id и
создайте профиль через POST /users/{userID}/profiles с `{"role":"staff"}`.
Переключитесь через POST /auth/switch-profile с полученным profile_id и используйте
новый access JWT. Получите ID справочников через GET /member-dictionaries.

Пример POST /members (ID статуса замените полученным из справочника):

```json
{"full_name":"Анна Иванова","date_of_birth":"1990-01-01","membership_status_id":1}
```

Ожидаются 201, Location, version=1 и пустые contacts/addresses. Добавьте контакт
с version=1; ответ вернёт карточку с version=2. Попытка изменить её с version=1
даст 409. GET /members/{id}/history покажет создание и контакт со снимками.
Проверьте поиск через GET /members?q=Иванова.

Вернитесь в admin, пригласите owner с club_member_id созданной карточки,
активируйте его через Mailpit и войдите. GET /members/me должен вернуть свою
карточку. Из отдельной сессии staff измените её статус на «Неактивный»:
тот же access владельца получит 403 на карточку и историю, но сможет открыть
/auth/profiles и переключиться на другой включённый профиль.

## Автоматические проверки и границы

```bash
gofmt -l cmd internal migrations api
go test -race -count=1 ./...
export DOGCLUB_TEST_DATABASE_URL="$DATABASE_URL"
go test -race -count=1 -tags=integration ./...
go vet -tags=integration ./...
go build -o bin/ ./cmd/...
go mod verify
git diff --check
```

Интеграционные тесты создают и удаляют только собственные одноразовые БД.
Проверяют права, членство, привязку, поиск/страницы, длинный email, чужие дочерние
записи, адрес мероприятия, конкурентные версии и откат при отказе записи истории.
Ответы роутера проверяются OpenAPI; логи — на отсутствие тела, query и токенов.

Настоящие migrate/admin/API дополнительно проверены с Mailpit на отдельной БД:
карточки, контакты/адреса, поиск, история, версии, привязка, неактивный owner с
доступным veterinarian, CSRF, блокировка, readiness и SIGTERM=0. Тестовая БД
удалена; рабочие карточки не создавались.

[Учёт собак](dogs.md) и связи dog_club_member используют
публичный members.Service для проверки владельцев в общей транзакции.
[Ветеринария](veterinary.md) и [мероприятия](events.md) используют публичные сервисы
для предметных проверок. Удаление людей и перепривязка аккаунтов не реализованы;
UI и внешняя почта не входят в текущую серверную часть.
